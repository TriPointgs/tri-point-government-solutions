## Separate one-order buyer-payment invitation
The administrator workspace `/admin/buyer-checkout` is linked from Order operations. It issues a single-use 15-minute invitation for one exact existing test order after current merchant terms/configuration and quote-validity checks. Runtime gates require preview, TP_BUYER_PAYMENT_PREVIEW_ENABLED=true, TP_BUYER_PAYMENT_PILOT_APPROVED=true, and TP_BUYER_PAYMENT_PILOT_ORDER_ID equal to that exact order UUID. No actual gate or pilot ID is set by this implementation.

The buyer page `/buyer-preview/checkout` uses its own `__Host-tp_buyer_payment` Secure/HttpOnly/SameSite=Strict cookie, one-hour server-enforced session, secret-hashed private `buyer-payment` storage and a seal over the order, saved terms acceptance and shipping address. It does not reuse or upgrade `__Host-tp_buyer_order` read-only links, administrator cookies or original cart ownership. Anyone holding the invitation can redeem it; no email verification or automated delivery is implied. The token travels in a URL fragment, is removed from visible browser history at initialization, is redeemed only by explicit same-origin POST and is never kept in Web Storage. GET pages never consume the invitation.

The buyer sees the order's retail items/totals and exact current approved terms. The source terms must match the immutable order's accepted version and content digest; drafts are never treated as approved policy. Two explicit consents are required before opening Stripe TEST Checkout. The exact accepted request and terms digest are durably saved and independently read back first. Equivalent request field order uses a canonical digest. After an uncertain reply or browser reload the saved request identity is recovered, so the same order/Stripe Session is resumed instead of a replacement payment being created.

A server-side adapter selects the original owner/order; browser-supplied owner, order, amount, account or paid overrides are rejected. The response contains only a restricted buyer projection or a validated exact checkout.stripe.com HTTPS destination. No addresses, customer email, payment identifiers, supplier account references, costs or administrator permissions are released to the buyer.

The existing cart checkout service accepts an internal authorization callback; the Stripe bridge invokes it after merchant account verification and immediately before Session creation. Source freshness, original policy and grant validity are rechecked at this point; revocation or expiry during a delayed account lookup blocks creation. Grant validity is checked again before returning the URL/data. These checks cannot retroactively cancel a Session or reverse a payment already created or in flight. Replacement/revocation/logout end application access only; closing an existing Stripe Session remains the separate merchant operation. This limitation is stated on the page.

## Buyer return and payment recovery
Existing Stripe Session parameters and idempotency keys are unchanged, including the original neutral return URL. The neutral return page now loads a module script that performs a same-origin, read-only, exact-order authorization check. A valid buyer-payment cookie routes to the buyer page; otherwise the existing staff checkout destination is retained. This preserves existing Sessions and their byte-equivalent retry parameters instead of changing return URLs beneath the same Stripe idempotency key.

The same-origin check is intentionally after the cross-site landing to retain Strict cookies without weakening them. Neither the landing URL nor a successful return claims payment. The buyer can explicitly recheck the existing test payment; verified signed events can also update saved payment state before a browser return. Expired quotes still permit reconciliation of existing payments, but hold fulfillment and prevent new checkout. A missing/expired/revoked buyer session cannot recover access from an order UUID in a URL; staff must review/reissue access. No refund, cancellation or replacement payment is inferred.

## Unified buyer-safe fulfillment
`lib/buyer-fulfillment.mjs` combines saved read-only handoff and UAT-dispatch state. Once an actual saved test-dispatch attempt exists, the older handoff's tracking is deliberately not reused: it belongs to a separately scoped supplier reference. The buyer sees test acknowledgment, rejection, review-required or stale status, never production-order or delivery confirmation. Stale/missing/future observations cannot remain current acknowledgments.

Before a dispatch attempt, fresh matching handoff tracking remains available. Only recognized carrier/number pairs are returned, with URLs reconstructed by the existing allowlisted carrier builder. Unknown fields, supplier references, costs and raw external URLs are omitted. GET status reads do not poll Stripe or TD. The previous buyer-page statement that the site had never submitted an order was narrowed to production orders so it does not contradict a future enabled test pilot.

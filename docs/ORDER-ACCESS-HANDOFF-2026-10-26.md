# Two-feature marketplace patch: buyer order access and supplier handoff

## Scope / starting truth
Repository TriPointgs/tri-point-government-solutions; feature/td-product-controls; draft PR #23. Starting head/rollback: 4d0942ca9816b9f6299bfecd3ae3e41a83db0caa. Main observed at start: c61404dcd184b5c1e43a40b73e86c740b4ee375a. User requested at least two compatible improvements in one patch. Neither a permanent buyer-account policy nor a real supplier purchase was approved, so this patch implements two complete private-preview features without pretending those larger launch decisions are finished.

## Feature 1 — buyer-facing read-only test-order access
`/buyer-preview/order` renders a buyer-safe order summary without requiring an administrator or original cart cookie. It uses an explicitly issued one-order invitation, not a login/account migration or verified email identity. Anyone holding the invitation can redeem it; delivery is manual and no email is sent.

Only an authenticated administrator can issue/revoke a link at `/admin/order-operations`. Issuing requires the exact existing immutable test order, expected access revision and explicit consent. The link expires in 15 minutes, is consumed once, and becomes a separate one-hour server-validated session using a Secure/HttpOnly/SameSite=Strict `__Host-` cookie. Storage contains only the secret hashes. Replacement and revocation invalidate prior invitations and sessions. Concurrent redemption allows one winner. A final access check before returning order data handles revocation or expiry while the request was in progress.

The invitation is passed in a URL fragment, removed from browser history on page initialization, never sent in a GET/query/referrer and never placed in Web Storage. Page GET does not consume the invitation. Explicit redemption is required. Reloading saved status does not query Stripe or TD. The buyer projection excludes contact/address data, payment identifiers, supplier PO/account references, costs, margins, licenses and serials. It does not grant access to checkout writes or administration. An order UUID or administrator cookie alone is not buyer access.

This feature remains disabled unless the separately reviewed private-preview flag TP_BUYER_ORDER_PREVIEW_ENABLED is true. No actual environment flag was enabled by the implementation. This is not guest purchasing, permanent accounts, verified email, automatic invite delivery or public launch.

## Feature 2 — durable supplier handoff and exact UAT reconciliation
The same operations page can prepare a server-owned handoff for an existing finalized test order. Preparation rechecks full captured Stripe test payment and approved sourcing, current cart/product/price/shipping/policy conditions and the original quote. A valid preflight is a time-limited observation only: supplier submission remains false, and a later adverse payment update removes a current pass on saved reads.

The deterministic TPTEST reference is bound to the merchant, current configured supplier scope and exact order. A changed merchant/supplier account cannot reuse another account's handoff. Revision checks and request IDs prevent duplicate records and permit exact saved-result replay after an uncertain response. Uncertain, missing or changed observations never cause another purchase attempt.

Reconciliation reuses only the existing TD read-only GetOrderStatus adapter and requires an explicitly enabled UAT connection. TEST handoffs cannot query production supplier order status. Every sales order must match the exact saved reference; products require exact TD SKU, manufacturer part and ordered quantity. Missing, duplicate, conflicting or kit/bundle product data is held for review. Parent/subline/package quantities are not added. Matching, fresh observations supply only sanitized recognized-carrier tracking to the buyer portal; supplier text and tracking numbers are not independent delivery confirmation. Provider errors and stale observations remove current buyer tracking.

There is deliberately no SubmitPO adapter or purchase payload dispatched by this feature. It is supplier preparation plus read-only reconciliation, not completed automated purchasing/fulfillment. TP_SUPPLIER_HANDOFF_PREVIEW_ENABLED is separately gated and not enabled by this patch. No cron, automatic polling, refund or customer mail is introduced.

## Shared boundaries
Both services use private account-scoped extension storage at `preview/order-extensions/v1/<merchant hash>/<area>/<order UUID>.json` with separate buyer-access and supplier-handoff areas. They use bounded reads, uncompressed strong-version reads and conditional writes; no unconditional overwrite on conflict. Immutable order seals prevent cross-owner/order replacement. The existing shop serverless function routes both features, so no new serverless function is added. Production routes reject these features. Existing branding, merchant setup, core checkout and unrelated projects remain unchanged except navigation/routing hooks.

## Verification before hosted deployment
The final local suite contains 1,130 tests: 1,123 passed, zero failed and seven intentionally skipped opt-in hosted diagnostics. The entire suite passed three separate runs: sequential concurrency 1; randomized concurrency 4, seed 20261025; randomized concurrency 8, seed 7319. Clean preview and production-mode builds also passed (25 and 24 generated pages); a production-mode build is not a production release.

Fifty-seven new regular tests cover capability scope, secret hashing, expirations, concurrent grants/redemptions, revocation, logout, in-flight revocation/expiry, original ownership, private projection, origin/role/cookie/query restrictions, storage isolation and bounds, failed writes, payment-before-handoff, quote expiry, policy changes, UAT-only reads, exact reference/product/quantity matching, duplicate split-order ambiguity, stale tracking, supplier-account changes and adverse-payment holds.

`scripts/verify-order-operations-browser.mjs` exercises actual local HTTP handlers in desktop 1440px, touch-mobile 390px and keyboard-tablet 768px Chromium runs. Separate administrator and buyer contexts use distinct cookies. The buyer starts with no administrator/cart cookies. Tests verify explicit redemption, history fragment removal, no token URLs, lack of admin permission, exact totals, matched carrier link, replay denial, reload, revocation, same-page replacement invitation, logout and layout overflow. All passed with no script errors or uncontrolled external requests. Providers are synthetic; no actual Stripe/TD calls occurred. Existing checkout and merchant-setup browser suites also passed in all three modes.

A new real browser regression was fixed: replacing the invitation in the fragment of an already-open page did not reinitialize access. Fragment changes now reload and require a fresh explicit redemption. The browser harness also exposed the packaged Chromium single-process mode's unreliable isolated-context cookie reporting; the new harness disables single-process and keeps web security enabled. It asserts the buyer cookie and admin denial rather than trusting an empty cookie listing. A test initially compared cache-control directive order; it now checks the identical required directives regardless of order.

Production dependency audit reported zero known vulnerabilities at test time. This is not a penetration-test certification. Session design reference reviewed: OWASP Session Management Cheat Sheet (https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

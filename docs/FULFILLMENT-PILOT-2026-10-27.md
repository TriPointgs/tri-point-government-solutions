# Fulfillment continuation — supplier submission recovery and order-update drafts

## Baseline and scope

Main was independently observed at 307e07d17a17918299181b031ced24768b5cd2eb, changed externally since the previous checkpoint. This patch does not merge, rebase, update main, or publish production.

User requested continued marketplace work. This stage implements a separately gated TD UAT supplier submission/recovery path and a durable order-update draft queue. Tests use injected synthetic payment and supplier responses. No live payment, actual TD UAT submission, production purchase, customer email or refund is authorized or initiated by this task.

## Supplier contract source
Implementation follows the user-supplied `openapi (2).json` in the project Library: SubmitPO POST, contract 3.1, and GetPOStatus POST, contract 2.6. Relevant definitions are OrderRequest, OrderResponse, SubmitPORequest/Response and OrderStatusQuery/Result. Original file regions: 1191–1387 (SubmitPO route/examples), 2861–3345 (request/acknowledgment fields), 4765–5264 (PO-status response). Raw-byte materialization was unavailable, so extracted file content was read directly. The original private document was not copied into this public repository.

OAuth payloads omit legacy Credential/CustomerNumber. Header acceptance alone is not enough: every returned line must match saved PO/line/SKU/manufacturer part/quantity and an SO sales-order identity. Top-level service errors, nested validation errors, partial/backordered/manual/ambiguous results, transport errors and unreadable responses cannot become accepted orders. Contract 3.1 does not return SynnexUnitPrice/AcceptedQuantity; the acknowledgment is not final supplier-cost evidence. A notFound status does not clear an attempted order or permit automatic resubmission.

## Implemented supplier pilot
`/admin/fulfillment-pilot`, linked from Order operations, prepares and reviews one exact approved test order. The UAT adapter uses separate TP_TD_UAT_* credentials and fixed UAT endpoints, not the existing production read-only credential configuration. Configuration requires explicit UAT approval, exact pilot order UUID, USD account-currency confirmation and a goods-cost ceiling. Submission additionally requires TP_TD_UAT_SUBMIT_ENABLED=true and per-action consent. No flags or actual credentials were added or enabled by this task.

Preparation requires a finalized paid test order, current server-verified capture, approved sourcing and a nonexpired original quote. It requests exact UAT supplier prices and one complete UAT freight shipment. UnitPrice is acquisition cost, never the customer's marked-up price. The restricted pilot uses US addresses, one parcel shipment, no backorders and complete shipment; these are pilot limitations, not adopted public customer policies. ZIP strings retain leading zeros. Supplier freight remains an estimate, not guaranteed final cost; the configured ceiling applies to goods, not unknown future fees.

The plan is sealed to the immutable order plus private destination/name, supplier credential scope, exact cost/service and a deterministic test PO reference. Its private payload is stored only in private Blob. Administrator projections omit the shipping address, contact email, credentials and raw payload. Fresh server-created plans are frozen and branded in memory before the transport can submit them. Replanning at submission must match the reviewed payload exactly. A second source/payment/order check after OAuth and immediately before the HTTP write catches changed policy, stale capture, altered destination or a lost dispatch claim.

A one-shot send intent is conditionally persisted and independently read back before any supplier POST. Only one competing caller can own it. Once attempted, no new request ID, timeout, malformed response, explicit rejection, missing supplier record or process interruption can clear it for another automated submission. The only recovery operation is an exact-reference GetPOStatus read. An uncertain store completion preserves the sending/uncertain state. This intentionally prefers staff review over duplicate purchasing. No Stripe capture/refund creation is included; the existing payment is only checked.

New modules: td-po-contract.mjs (pure contract validation), td-po-uat.mjs (gated UAT transport), supplier-dispatch.mjs (durable state machine). New private storage area: supplier-dispatch. Existing read-only handoff behavior is not relabeled as purchasing.

## Implemented order-update draft queue
The order-updates storage area saves deduplicated message snapshots derived only from server-owned finalized order/payment/supplier state. It prepares order received, test capture observed, supplier UAT acknowledgment and review-required notices. A stable fact generates one draft even across repeated synchronization. Superseded facts remain historical and are labeled as such. Timestamps describe the saved snapshot, not a continuously verified current state.

The queue has no recipient, email-provider transport, delivery status override or dispatch endpoint. All records remain draft-not-sent; emailSent/dispatchEnabled are false. Messages do not treat a supplier acknowledgment as a shipment, tracking as delivery, capture as bank payout, or rejection as a refund. Browser-supplied recipient/message/approval fields are rejected. Saved reads and draft synchronization do not make Stripe or supplier calls.

## Routing and boundaries
Both features use existing api/shop.js through authenticated, same-origin, rate-limited preview-only routes. No new serverless function or cron. api/shop.js maxDuration is now 120 seconds to accommodate bounded serial sourcing/payment/OAuth checks. Vercel's documented per-function maxDuration configuration was consulted; this does not alter public release gates. Anonymous, contractor and buyer-cookie access cannot use these administration endpoints. Runtime settings and configuration fields never expose secret values.

# Marketplace release runbook — gates, not an automatic deploy instruction

1. **Baseline and backup:** Read current main and review-branch SHAs, reconcile newer corporate/blog content, verify unchanged logo hashes, preserve rollback deployment and data snapshot. Do not merge an old feature branch over newer production work.
2. **Eligible products and infrastructure:** Select documented sellable SKUs/brands, verify content/image licensing, manufacturer restrictions, new/refurbished condition, real USD prices and stock. Move the catalog to an approved always-on host or establish an explicitly accepted monitored arrangement; verify daily/current source ingestion before relying on it. Do not publish all source records by default.
3. **Payment and tax sandbox:** Connect the approved Tri-Point payment account; never reuse an unrelated business's account. Use test keys in test environments. Verify signed raw webhook payloads, duplicate/out-of-order events, total/currency/order binding, stock/price drift, tax/address changes, authorization expiry, capture/refund and failed-payment paths. Browser return pages alone cannot prove payment success.
4. **Supplier order sandbox:** Use the supplied current TD contract, not deprecated routes. SubmitPO is documented as POST /api/v1/webservice/json/SubmitPO; GetOrderStatus and GetPOStatus expose status/shipment detail. Preserve a stable unique internal PO and durable dispatch intent. An HTTP 200 or an accepted header alone is not proof every line was accepted. Bind every returned line/SKU/quantity to the order. A timeout requires querying/reconciling the existing PO before retrying. Real endpoint/account permissions and order behavior are not yet verified.
5. **Communications and customer access:** Use the already verified Tri-Point sender domain with approved addresses; wire a persistent transactional outbox with event IDs and retry/reconciliation state. Verify received versus authorized versus paid versus shipped wording. Test split shipments and actual tracking data. Provide authenticated/scoped customer access, not a public lookup that exposes a guessable order record. Test email delivery rather than equating an API acknowledgement to inbox receipt.
6. **SEO/publication:** Approve public canonical product/category routes and licensed public images. Ensure initial HTML has accurate identity, copy, safe metadata and the current permitted Offer fields. Remove authentication/noindex ONLY from approved public product/catalog pages, not cart/account/admin/API/private drafts. Generate filtered/split sitemap and index; check robots and canonical behavior, Rich Results, missing/discontinued product statuses, mobile rendering and accessibility/performance. Verify Search Console and Merchant Center ownership; submit only released, accurate URLs/products. No fake reviews, badges, discounts or delivery guarantees.
7. **Explicit live pilot and go/no-go:** With owner approval, run a low-value real transaction, supplier acknowledgement, payment capture, confirmation email, package tracking, customer view and refund/cancellation drill as appropriate. Record provider evidence without publishing personal data or secrets. Confirm alerting, support handoff, rollback and reconciliation. A READY code deployment alone is not a passing live pilot.

Public launch is held until the listed provider integrations, policy decisions and live checks are complete. No live purchase, account connection, paid infrastructure subscription, email campaign or search-engine submission is authorized by this document itself.
